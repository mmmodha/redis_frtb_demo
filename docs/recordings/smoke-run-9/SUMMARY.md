## Single named hypothesis for Wave 5.15f

**`calc-per-bucket-fanout-cluster-routing`** — `services/api/src/routes/calc.ts`
discovers buckets cluster-wide via `FT.AGGREGATE idx:sens … GROUPBY
@bucket` (which ioredis Cluster aggregates correctly across masters),
then fans out one `FT.AGGREGATE @risk_class:{X} @bucket:{Y}` per bucket
to compute K_b / S_b / count. The per-bucket fanout is dispatched
per-shard the same way the Wave 5.15c precondition probe was, so it can
land on the empty master (16.59.25.183) where 0 sens:* keys live and
read `count=0`. The fix family is the same as 5.15d.1 — either route
the per-bucket aggregation via the cluster-aggregated path used by the
discovery query, or fan to all masters and sum the partial K_b / S_b.

A second, independent issue worth scoping (lower priority because it
does not break AC1 on its own): the generator emits 300 k stream
entries that collapse to 126 k unique sens:* hash keys
(`xlen / num_docs = 2.37` collision ratio). This is what dropped the
density gate from the runbook's 80 % target to 42 %. Investigate
whether the generator's `sens:{trade_id}:{factor}` key derivation is
intentionally collision-prone or whether it should include a
sequence/timestamp suffix.
