RediSearch TAG matching is case-insensitive by default, which is why step
7's bucket-discovery `FT.SEARCH @risk_class:{girr}` *did* return the
expected JPY/AUD/SEK/OTHER (GIRR), 13/3/6/12/7/2 (EQUITY),
USDCHF/EURJPY/GBPJPY/USDCAD/AUDUSD (FX) buckets — so the response shape
is "200 + correct per_bucket array, every K_b/S_b/count = 0".

## Named hypothesis for Wave 5.15l: `calc-api-risk-class-case-pass-through`

The Wave 5.15f case-alignment fix corrected `SENSITIVITY_TYPES` in the
generator. There is a **second, structurally identical** case-mismatch on
the calc path that was masked by the first one — every smoke run since
5.13 RED-ed on the `sensitivity_type` mismatch, so the calc never SCAN-ed
far enough to expose it.

**Failure mode** (smoke-run-12, evidence in this run):
- Generator writes `sens:{GIRR:JPY}:01…` (UPPERCASE `GIRR` in hash-tag).
- `services/api/src/routes/calc.ts` line 152: `const risk_class =
  req.body?.risk_class;` — reads the user-supplied value as-is.
- Calc payload from `scripts/run-calc.sh` is
  `{"risk_class":"girr","sensitivity_type":"delta"}` (lowercase).
- Line 227 of `routes/calc.ts`: `routeKey = sens:{${risk_class}:${b}}:_route`
  — builds **lowercase** routing key.
- Line 233 passes `risk_class` (lowercase) as the first FCALL argument.
- `services/calc/lib/girr_delta.lua` line 20: `local pattern = 'sens:{' ..
  risk_class .. ':' .. bucket .. '}:*'` → **`sens:{girr:JPY}:*`**.
- SCAN with that pattern finds **0** keys on every shard (forensic:
  `logs/per-shard-sens-scan.json` shows 8450 keys for the UPPERCASE
  pattern `sens:{GIRR:JPY}:*` on shard B); `count=0` → `K_b=S_b=0` →
  `charge=0`.
- Bucket discovery (`@risk_class:{girr}` FT.SEARCH at line 181) *does*
  find buckets because RediSearch TAG matching is case-insensitive by
  default, which is why the response is `200 + populated per_bucket
  array` rather than a 503/empty result.

**Why this wasn't a smoke-run-10/11 finding:** runs 10 and 11 RED-ed on
the prior `sensitivity_type` mismatch — keys carried `"DELTA"` /
`"VEGA"` (UPPERCASE), so even if SCAN had matched, the Lua row filter
`doc.sensitivity_type == 'Delta'` would have dropped every row. With
that fix now in place (verified end-to-end in this run via the on-disk
shape gate at step 6.5), the second mismatch is the active blocker.

**Single-symbol fix candidate** (Wave 5.15l — *not* attempted in this
wave per the "NO code changes" scope): normalise `risk_class` to upper
case at the calc API entry point in `services/api/src/routes/calc.ts`
(one `.toUpperCase()` next to line 152), so the FCALL routing key and
the Lua SCAN pattern both carry the canonical UPPERCASE form that the
generator already writes. The Lua-side alternative (`string.upper` on
the arg) is also one symbol but spread across 6 `.lua` files; the API
side is the smaller diff.

**Secondary observation (out of scope, do not act):** the 40.08 % density
under volatile-lru with 300,000 rows on a 2 × 700 MB cluster suggests
either the smoke `--rows` budget should drop to ~120,000 to fit
comfortably, or the schema's per-row JSON payload is larger than the
shard plan accounted for. Defer to whichever Wave 5 task owns the
sizing model; this run does not depend on it (DoD #9: density does not
block AC1).
